# Local Lessons Learned

- [Initial Setup]: Hub initialized with basic autonomous agent and workflows.
- [2026-08-05]: Discovered the autonomous agent never fetched real code from spoke repos - it only read lessons.md/NORTH_STAR.md and then asked an LLM to audit "the latest code" with none actually in the prompt. This produced ~2,000 hallucinated GitHub issues in one spoke (tso) over ~4 months. Fixed by fetching the spoke's latest commit diff and including it in the prompt, and by skipping the AI call entirely when there's no usable diff.
- [2026-08-05]: The AI's JSON response was trusted blindly - a parse failure fabricated a synthetic result and posted an issue anyway, and a successful-but-wrong-shaped response got string-interpolated straight into the issue body (producing literal "undefined" / "[object Object]"). Fixed by validating the response shape before ever calling `issues.create`, and skipping (not fabricating) on any failure.
- [2026-08-06]: Fixing the hallucination root cause wasn't enough on its own to trust re-enabling automation - a bug in a future prompt/model change could still refile the same mistake at scale before anyone noticed. Added two independent safety rails on top of the validation fix: a `DRY_RUN_MODE` env var (default on) that reports findings without ever filing them, and a hard `RATE_CAP_PER_REPO_PER_DAY` (default 3) once dry-run is off. Both fail safe - a missing/misconfigured env var means no issue gets filed, not the reverse.
- [2026-08-06]: `ai_decision_log.json` was part of the spoke setup contract from the start but nothing ever read or wrote it - real decision logging is now live. Every decision (skip, dry-run finding, rate-capped, created) gets appended with its commit sha, so the same commit+mode combination is never re-analyzed by the AI twice, and the last few decisions get fed back into the prompt so the model has memory of what it already decided instead of re-litigating it every run.
- [2026-08-06]: The "Recursive Learning Loop" the README described was aspirational - nothing aggregated insights across spokes automatically. Built `api/recursive_learning.js`: a monthly job that reads every spoke registered in `spokes.json`, looks for a pattern that recurs across more than one of them, and - if it finds one - opens a PR against this repo proposing an update to `universal_lessons.md`/`north_star_framework.md`. It never pushes directly to `main`; a human still reviews and merges. Seeded `spokes.json` with `tso`, the one spoke actually connected today.
- [2026-08-06]: `scripts/prune-logs.js` had been a no-op stub since the hub's first setup - "Pruner initialized..." and nothing else, never invoked by any workflow. Replaced with a real implementation: for every spoke in `spokes.json`, archive `ai_decision_log.json` entries older than a retention window into `ai_decision_log_archive.json` (archive written before the live log is truncated, so a mid-run failure can't lose data), then wired it into a weekly Sunday workflow. Runs as a plain Actions script, not a Vercel function - no AI involved, so it only needs a GitHub token, not the AI credentials.
- [2026-08-06]: `setup_spoke.py`'s generated `call-hub.yml` had two real problems: it only ever computed `debug`/`refactor` from an inline workflow expression (never `hunt`, despite the hub handler supporting it), and it baked the hub's URL directly into the curl command at generation time - completely ignoring the `VERCEL_URL` secret the README told operators to set. Fixed both: added a third cron for `hunt`, replaced the inline expression with a step-output `case` statement (matches the existing "prefer step-outputs over inline expressions" lesson in the hub's own `hub_lessons.md`), and switched the generated workflow to actually read `VERCEL_URL` (plus `VERCEL_BYPASS_TOKEN`) from secrets like the docs always claimed it did.
- [2026-08-06]: Only `tso` was ever actually wired to this hub, and even that was ad hoc - its workflow hardcoded the hub's URL directly rather than using the `VERCEL_URL` secret convention (that PR is up on the `tso` repo). `thinkos-server` and `tais` had zero integration at all - no workflow, no spoke contract files. Onboarded both via `setup_spoke.py`'s output (with real, project-specific `NORTH_STAR.md` content pulled from each repo's own README, not left as an unfilled template), and registered all three spokes in this repo's new `spokes.json`. Safe to leave the schedule enabled on the two new spokes immediately, since the hub's `DRY_RUN_MODE` defaults to on hub-wide - nothing files an issue until that's verified and flipped.
- [2026-08-06]: The `health-report.yml` this repo used to have was a non-functional copy-paste of `tso`'s own health tooling - it referenced `scripts/health-analyzer.js` and Prisma, neither of which exist here, and posted comments literally saying "Auto-generated by TSO Health System". Built a real, Mothership-native replacement (`scripts/health-report.js`): reports on the hub/swarm's own health per registered spoke (issues filed, decisions logged, skip rate, inferred live/dry-run status), published as a single pinned issue on this repo that gets updated in place rather than spammed on every run.
- [2026-08-07]: A debugging pass over the just-shipped sprints found four real gaps: `scripts/prune-logs.js` had no retry on a stale-`sha` write conflict (unlike the decision-log appender it shares a file with) - fixed by retrying the whole read-partition-write cycle. `scripts/health-report.js` never reopened the pinned report issue if a human closed it - future runs would silently keep rewriting a closed issue's body. `api/recursive_learning.js` hardcoded `main` as the base branch instead of looking up the repo's actual default branch. `api/autonomous_agent.js`'s "already decided" replay only surfaced a prior `created` decision's `issueUrl` nested under `priorDecision`, not at the top level where a live response puts it. All four fixed with test coverage.
- [2026-08-07]: The retry fix above for `scripts/prune-logs.js` introduced a subtler bug of its own: the retry loop re-reads and re-partitions the live log from scratch on every attempt, but the archive write inside that loop just appended `[...archiveEntries, ...old]` unconditionally. If the *archive* write on one attempt succeeded but the *live-log truncation* write right after it then failed (the exact scenario the retry exists to handle), the next attempt recomputed the same `old` set from the still-untruncated live log and appended it to the archive a second time - real, in-archive duplicate entries from a single invocation, not the "safe, idempotent on the next run" duplication the archive-then-truncate ordering is meant to allow for across separate runs. Fixed by deduping against already-archived entries (by timestamp+commitSha+mode) before writing, and skipping the archive write entirely when there's nothing new to add. Reproduced the bug in a standalone script before fixing it, and added a regression test to `dev-test-prune-logs.mjs` that asserts the archive ends up with exactly the moved entries, not doubled.
- [2026-08-07]: `setup_hub.py` - the installer this repo has carried since before any of the above sprints, meant to scaffold a brand-new hub from scratch - never generated any of the four `.github/workflows/*.yml` files (`self-reflect`, `prune-logs`, `health-report`, `recursive-learning`). Someone running it fresh would get `api/*.js` and `scripts/*.js` deployed to Vercel and committed, and nothing would ever actually invoke them - a hub that deploys cleanly and then sits completely inert, with no error anywhere to say so. This is the same class of gap `DOCS_VS_CODEBASE.md` exists to catch, just one level down: the installer's own claim (that running it produces a working hub) didn't match what it actually produced. Fixed by adding all four workflow files to its generated file list, embedded and kept in sync the same way `api/autonomous_agent.js` etc. already were, verified by diffing a scratch-dir install's output against the real files. Also caught `.gitignore`'s embedded copy had drifted (missing `.vercel`/`__pycache__/`/`*.pyc`, added to the real file at some point after this script was first written) - synced that too.
- [2026-08-07]: Every fix above this line was verified locally (`node scripts/dev-test-*.mjs`, `python3 -m py_compile setup_hub.py setup_spoke.py`) before it shipped - but nothing ran that sweep automatically. It only happened because whoever was making the change remembered to run it by hand, every time, after every merge. Half the defects logged above were sitting in code that already had a passing test - proof that "it passed its tests" only helps if something actually re-runs those tests on every future change, not just the one where they were written. Added `.github/workflows/ci.yml`: runs the full local sweep (all four `dev-test-*.mjs` harnesses, then `py_compile` on both installer scripts) on every pull request, on every push to `main`, and on demand. Needs zero secrets - every harness already runs against a fully mocked `octokit`/`fetch` - so it's safe to run even on a PR from a fork.
- [2026-08-08]: Finished the two things the CI workflow above deliberately left out, plus a third bug found while doing it. First, a `package.json` `"test"` script (`for f in scripts/dev-test-*.mjs; do node "$f" || exit 1; done`), with `setup_hub.py`'s embedded copy re-synced to match - CI now runs `npm test` instead of duplicating that loop inline. Second, a CI step that actually runs `setup_hub.py` into a scratch directory and diffs its output against this repo's real files (`api/*.js`, `scripts/*.js`, all four workflow YAMLs, `package.json`, `.gitignore` - deliberately excluding `spokes.json`/`universal_lessons.md`/`north_star_framework.md`, which are meant to diverge from this repo's live state), so a repeat of PR #13's bug (missing workflows in the generated output) would now fail CI automatically instead of waiting for someone to notice by hand. Third, found while writing that scratch-dir step: `setup_hub.py`'s own dependency install, `subprocess.run(["npm", "install"], shell=True)`, never actually ran `npm install` - combining `shell=True` with a list means everything after the first item becomes an argument to the *shell*, not to `npm`, so it silently ran bare `npm` (prints usage, does nothing) on every install, for as long as this script has existed. `node_modules` was never created; anyone who actually ran this installer got a hub with no `@octokit/rest` and no error saying why. Fixed by dropping `shell=True` (a plain list already execs correctly without a shell) and warning, not crashing, if `npm install` still fails for some other reason.
- [2026-08-08]: Every blocker left on this project traced back to one thing: the hub's Vercel deployment sits behind Deployment Protection, and getting a bypass token needs dashboard access nobody here has. Rather than keep waiting on that, added a full alternative hosting path: **`gas/`**, a Google Apps Script port of `api/autonomous_agent.js`/`api/recursive_learning.js`, deployed as a Web App - which has no deployment-protection-style wall to fight, since "Anyone" access is a normal, supported option. Same decision logic, same validation/dry-run/rate-cap rails, same decision-log dedup; three real platform differences accounted for: no `@octokit/rest` (`gas/github.js` is a small hand-rolled REST client on an injected HTTP primitive instead), no Node `fetch`/Promises (Apps Script's `UrlFetchApp` is synchronous, so this code is fully synchronous too, matching the platform instead of fighting it), and no local filesystem (the hub's own `universal_lessons.md`/`north_star_framework.md`/`hub_lessons.md` are fetched from this repo via the GitHub API instead of read off disk - arguably an improvement, since it means no redeploy is needed to pick up an edit to those files). `api/*.js` and the Vercel path are untouched and stay in the repo; dropping Vercel entirely is a deliberate future step once Apps Script is actually verified live, not bundled into adding the alternative.
- [2026-08-08]: Apps Script has no `import`/`export` - every file in a project shares one global function scope, closer to classic script concatenation than real ES modules. Learned this the concrete way: `gas/autonomous_agent.js` and `gas/recursive_learning.js` both declared `const DEFAULT_HUB_OWNER`/`DEFAULT_HUB_REPO`, which is completely harmless as two separate ES modules but is a real `SyntaxError` the instant both files share one Apps Script project's scope. Caught by the test harness itself - `scripts/gas-test-harness.mjs` loads the literal, unmodified `gas/*.js` source through Node's `vm` module the same way Apps Script combines files, specifically so what's tested is byte-for-byte what `clasp push` uploads, no bundler or compiled intermediate in between. Fixed by hoisting both constants into a new `gas/constants.js`, declared exactly once, loaded before anything that references them.
- [2026-08-08]: Also built a standalone **PWA dashboard** (`dashboard/`) for watching spoke health without waiting on the weekly pinned issue - a separate, additive piece, not a replacement for anything (a PWA can't receive GitHub Actions' POST mid-cron-job, so it was never a candidate to replace the Vercel/Apps Script backend). Since Mothership and every spoke are public repos, `dashboard/app.js` reads `spokes.json` and each spoke's `ai_decision_log.json`/issue list straight from `api.github.com`, client-side, computing the exact same metrics `scripts/health-report.js`'s `buildReportForSpoke` already does - no backend of its own, installable via `manifest.json`+`sw.js`, hostable for free on GitHub Pages. Verified the approach against real live data (not just by inspection): `spokes.json` fetched and decoded correctly; the issues-list call then hit GitHub's unauthenticated 60-requests/hour cap on this environment's shared IP, which is the exact limitation already disclosed in the dashboard's own footer and `app.js`'s header comment - confirmed the graceful-degradation path (`null` -> rendered as "n/a") is what actually fires, not a crash.

- [2026-08-10]: A UI/UX audit of `dashboard/` (the one real user-facing surface in this whole project) found 20 concrete issues, verified by actually loading the page in a real headless browser against mocked and live `fetch()` responses rather than just reading the code. The most consequential: `fetchDecodedFile`/`countIssuesCreatedSince` collapsed every failure - a genuine outage, a 404 on a file that doesn't exist yet, and hitting the disclosed 60-req/hr rate cap - into the same bare `null`, which then rendered as the same **critical/red** "no decisions logged" chip as an actual problem. Hitting the rate limit (the single most likely real failure mode, per the dashboard's own footer) painted every spoke red, indistinguishable from a real outage. Fixed by propagating a real `{ ok, rateLimited }` result through the fetch helpers instead of a bare `null`, giving "rate-limited," "couldn't load," and "no decisions logged this window" three distinct, correctly-colored states (warn/critical/neutral respectively) - confirmed via a mocked-`fetch` browser test asserting each renders its own chip class, not just by reading the code. Also fixed a real race condition (clicking Refresh twice while a load was in flight produced duplicated rows - confirmed by reproducing it, then confirming a disabled-button guard closes it), parallelized what was a serial per-spoke fetch loop, added severity-based row sorting, mapped raw `outcome` enum values to human labels, and a batch of accessibility/PWA fixes (`aria-live` on the status line, focus-visible styles, a table caption, "opens in new tab" hints, a `color-mix()` fallback background, service-worker `skipWaiting`/`clients.claim` plus an install-failure `.catch` and an offline fallback response, and `apple-touch-icon`/manifest PNG + maskable icons rendered from `icon.svg` via headless Chromium - `rsvg-convert`/ImageMagick/`sharp` were unavailable in this environment, so Playwright's pre-installed browser did the SVG→PNG conversion instead). One thing learned along the way while building the rate-limit detection: a cross-origin `fetch()` to `api.github.com` can't reliably read `x-ratelimit-remaining` (browsers only expose CORS-safelisted response headers to JS unless the server adds `Access-Control-Expose-Headers`) - confirmed by a mocked-header test that initially failed silently - so the fix treats any 403 from this API surface as a rate limit (every endpoint this dashboard calls 404s on a missing resource, not 403) rather than depending on a header that may not be visible at all.

- [2026-08-10]: A second UX pass over `dashboard/`, this time hunting specifically for "invisible until it matters" gaps rather than visible bugs (the first pass already fixed those). The most consequential: a single malformed `spokes.json` entry (a stray `null`, or an object missing `owner`/`repo`) used to throw inside `buildReportForSpoke`, and the old `Promise.all` fan-out rejected for *every* spoke on that one bad entry with no `.catch` anywhere - the whole dashboard silently wedged on "Loading…" forever. Fixed by filtering malformed entries out at parse time and switching the per-spoke fan-out to `Promise.allSettled`-shaped isolation (each spoke's own try/catch, `safeBuildReport`) so one spoke's surprise is that spoke's problem, never everyone else's - and as a direct side effect, rows now stream in as each spoke resolves instead of all waiting on the slowest one. Also added: a 15s `AbortController` timeout on every fetch (a hung request used to leave the Refresh button stuck disabled forever, with no recovery short of a hard reload); a 45s `sessionStorage` cache with stale-while-revalidate (repaint instantly from cache, "(cached)" labeled, while a background refetch patches the row in place - guarded against private-browsing/quota errors, and deliberately never caches a failure status, only real successful reports) given the dashboard's own disclosed 60-req/hr cap; a keyed row-reconciliation renderer (`renderRows`/`updateRow`) replacing the old clear-and-rebuild, so a manual Refresh no longer blanks the table before repopulating it - existing rows just update or get patched in place; a `document.title` marker for backgrounded/pinned tabs when a spoke is in a genuine failure state (deliberately NOT for the benign, disclosed rate-limited state - only a real "couldn't load"/"timed out" should make a background tab worth checking); and a live "updated Xs/Xm ago" relative timestamp instead of a frozen absolute one. Verified every one of these against the real page in headless Chromium with mocked routes, not just by reading the code - including a scratch copy with a shortened timeout constant specifically to prove the `AbortController` path fires and recovers the UI without waiting out the real 15s in the test itself.
- [2026-08-10]: A third audit of `dashboard/` (told explicitly to be honest rather than pad the list if little was genuinely left) caught something real in the *second* pass's own not-yet-merged work: the sessionStorage cache never actually skipped a network call. `loadDashboard`'s per-spoke loop read the cache to paint an instant placeholder, then unconditionally still called the real 2-requests-per-spoke fetch regardless of whether that cache was fresh - directly contradicting the code's own comments (and this file's prior entry above) claiming it "avoids paying for the same answer twice." The second pass's own verification test happened to assert this buggy behavior as correct (it checked a revalidation *did* happen on a second load within the TTL window, without checking whether it *should* have been skipped) - passing tests proving the wrong thing, the same class of trap this whole file exists to catch. Fixed by adding a `force` parameter to `loadDashboard`: passive triggers (initial load, and two new ones below) skip the network entirely when a spoke's cache is still within `CACHE_TTL_MS`, while an explicit user action (Refresh click, `'r'` keypress) always forces a real fetch regardless of freshness - a user who just asked for current data shouldn't silently get served something up to 45s old just because the cache's own clock calls it "fresh enough." Verified directly by counting mocked-route hits (not just watching the screen): a passive re-check within the TTL window adds zero requests; an explicit Refresh within that same window still adds a full fresh fetch; and after the TTL genuinely expires (tested via a scratch copy with `CACHE_TTL_MS` temporarily shortened, same technique as the prior timeout test), a passive re-check does refetch. On top of the fix: a `visibilitychange` listener refetches on return-to-tab (deliberately unforced, so it only spends anything on what's actually stale per spoke - a blind polling interval was considered and rejected, since its safe cadence shrinks every time `spokes.json` grows a spoke, while a cache-gated visibility trigger doesn't need re-tuning); an `online` listener self-heals the moment connectivity returns instead of waiting for a manual click; a `<link rel="preconnect">` to `api.github.com` so DNS+TLS setup starts before the first `fetch()` call rather than at it; and a live "retry in Xm/Xs" countdown for the rate-limited status (reusing the existing 15s render tick) instead of a frozen absolute retry time. Explicitly declined one item the audit raised and then talked itself out of: per-row screen-reader announcements as cached rows get patched with fresh data - the existing `#status` live region already brackets the whole load with a clear start/end announcement, and per-row chatter as background fetches resolve underneath a screen-reader user would be more disruptive than helpful.
- [2026-08-10]: Asked how to limit hosting requirements and maximize functionality without required connections - researched both halves of the system rather than guessing. **Backend:** investigated whether `autonomous_agent.js`/`recursive_learning.js` could run as a plain GitHub Actions script (zero external hosting at all), triggered by a spoke firing `repository_dispatch` instead of POSTing a URL - confirmed this is technically *less* migration work than the `gas/` port already completed (`processRequest`/`runRecursiveLearning` already read config straight from `process.env`, and a Node Actions runner already has native `fetch`, unlike Apps Script). But it has a real cost: every spoke would need its own PAT with write access to the Mothership repo just to fire the dispatch - a brand-new credential type spokes never hold today (they currently POST a plain URL, no credential at all), and that's a real new attack-surface increase that scales with spoke count. Presented the trade-off; decided to keep the existing hosted-URL model (Apps Script) rather than take it on - `gas/` already fully solves "limit hosting requirements" for the backend (no GCP billing, no Vercel-style Deployment Protection wall to fight) without introducing any new credential-distribution risk. Not building the Actions-only path; noting the decision here so it isn't silently re-litigated later without remembering why. **Dashboard:** confirmed via a real headless-browser test (not just reasoning, and bypassing this sandbox's own TLS-proxy artifact with `ignoreHTTPSErrors: true` to see genuine behavior) that opening `dashboard/index.html` directly as a `file://` URL - true zero-hosting - does not work for live data: GitHub's API rejects the `file://` page's `null` origin via CORS (`No 'Access-Control-Allow-Origin' header is present`), and the service worker refuses to register under `file://` at all (`file://` isn't a "secure context"). This is a hard, confirmed platform constraint, not something fixable client-side. The real, useful finding: the bar is still much lower than "use GitHub Pages" implies - any plain static HTTP(S) server clears it, including `python3 -m http.server` on your own machine. Documented this precisely in `README.md` instead of only ever mentioning GitHub Pages. Separately, added real durable offline capability: a `localStorage` "last known good" layer (no expiry, survives across browser sessions - distinct from the existing 45s `sessionStorage` cache, which exists only to cut request volume and deliberately forgets everything when the tab closes) that a genuinely offline load - a brand-new tab, zero network, possibly days later - falls back to instead of a bare failure message, for both the per-spoke data *and* the `spokes.json` registry itself (missing the latter would have meant the whole per-spoke fallback never even ran, since a failed `spokes.json` fetch returns early before reaching the per-spoke loop - caught this during design, not after). Rendered with an explicit "(offline - last seen 3d ago)" label and forced to a neutral chip color regardless of the historical status, so a days-old "live" can never misread as "currently fine" at a glance. Verified end-to-end with real browser sessions sharing `localStorage` across separate tabs (one online tab writes the fallback data, a second brand-new offline tab reads it back correctly, including when `spokes.json` itself also fails), a never-before-seen spoke correctly falling through to the plain failure message with nothing to recover, and a simulated private-browsing-style storage failure (`localStorage` throwing on every access) degrading to "no offline fallback" without crashing anything.
